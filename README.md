# Arpita & Swagat — wedding invitation

The existing React, TypeScript, Vite, MUI and Framer Motion invitation, organized into focused feature components.

## Run locally

```sh
npm install
npm run dev
```

On PowerShell with restricted script execution, use `npm.cmd` in place of `npm`.

```sh
npm run build
npm run preview
```

## Experience and code

`App.tsx` controls two states: the animated envelope overlay and the continuous invitation. The envelope itself and **Open Invitation** both trigger the existing opening sequence and music from the user interaction. `pages/WeddingInvitation.tsx` composes the page, beginning with `GaneshBlessing`. The blessing is a normal scrollable section with no additional click.

Feature folders under `src/components/` contain the envelope, blessing, hero, couple, event timeline, effects, music, countdown, locations and footer. Shared artwork, photo rendering, detail icons and scroll reveals live in `components/shared/`. Feature styles stay alongside their components; common invitation styling is in `src/styles.css` and theme tokens are in `src/theme.ts`.

There is one audio element and one `useWeddingAudio` lifecycle in App. The main-page music toggle controls that same element. Missing audio and blocked playback do not stop the invitation from opening. Refresh returns to the envelope.

The main page has nine subtle falling petals on mobile and sixteen on wider screens. Their configurations remain stable across renders, they never intercept clicks, and they are not rendered when reduced motion is requested. Reduced motion also simplifies the envelope and section reveals.

## Content and photographs

All wedding information, event details, residence address, dress codes and media paths live in `src/data/wedding.ts`. The event cards provide the complete dress-code guidance, so there is no duplicated standalone dress-code section. The relationship-duration section and copy have been removed.

Original photographs remain in `assets/`. Optimized responsive WebP copies and the supplied audio are in `public/assets/`. To regenerate them, run `npm run optimize:photos`. Faces are not retouched; images preserve their proportions.

There are no supplied ceremony-specific photos. Each event has a distinct decorative fallback. To add photos, place these files in `public/assets/events/`:

- `engagement.webp`
- `mehendi.webp`
- `haldi.webp`
- `wedding.webp`
- `reception.webp`

The paths are configurable per event. Files in that folder are discovered by Vite; absent files use the decorative artwork without making a failing image request. JPG, JPEG, PNG and AVIF are also supported when the configured filename matches. Corrupt images gracefully fall back to the artwork. Rebuild before deploying newly supplied images.

Google Maps URLs are generated by `src/utils/maps.ts` from the supplied venue names or residence address, without coordinates. The countdown targets `2027-02-10T12:00:00+05:30`; wedding-day messaging uses the Indian calendar day independently of the guest’s timezone.

## Verify

Start the dev server, then run:

```sh
node scripts/verify.mjs
```

The checks use Chrome at its default Windows location. Set `CHROME_PATH` for another installation and `TEST_URL` for a different preview URL. Tests cover 320, 375, 390, 430, 900 and 1440px widths, both opening triggers, keyboard access, the blessing-first scroll flow, one audio instance, music controls, exact event/family details, maps, stable petals, mobile/desktop timeline arrangement, photo loading, overflow, refresh, reduced motion, unavailable audio, rejected playback and IST countdown boundaries. Screenshots are saved in `test-results/`. Network fonts are replaced with system fallbacks during these checks.

Build and deploy `dist/` to a static host such as Vercel. Google Fonts have system-serif fallbacks when unavailable.

The footer RSVP submits to Google Apps Script. Both tabs already have the expected headers; the script appends rows without changing them. `main` and `bride` send to **Bride**, and `groom` sends to **Groom**.

## Connect RSVP

1. In the existing spreadsheet, choose **Extensions → Apps Script**.
2. Replace `Code.gs` with the contents of `apps-script/Code.gs` in this repository and save.
3. Choose **Deploy → New deployment → Web app**. Set **Execute as: Me** and **Who has access: Anyone**. Authorize access to the sheet and deploy.
4. Copy the web app URL ending in `/exec`. Copy `.env.example` to `.env.local` and replace `VITE_RSVP_SCRIPT_URL` with that URL. On your hosting provider, add the same environment variable.
5. Restart the dev server or rebuild/redeploy the site. Environment values are embedded at build time.

The branch is detected from Vercel, Cloudflare Pages, or local Git. Set `VITE_RSVP_BRANCH=main`, `bride`, or `groom` explicitly for other hosts, builds without Git, or preview branches. Unknown branches fail instead of writing to the wrong tab. All three deployments use the same Apps Script URL and spreadsheet. No content changes or new branches are created by this integration.

The existing loading, confirmation and retry UI is preserved. Confirmation requires a readable `{ "ok": true }` response; missing configuration or a failed save uses the existing error state. Submission IDs prevent duplicate rows when retrying the same unchanged form in the current page session. Declines save zero guests and false event selections. Do not use `no-cors`: its opaque response cannot confirm a save.

After deployment, submit an attending and declined response and verify the appropriate tab. Live saving cannot be tested until the Apps Script URL is configured. When changing the script later, use **Deploy → Manage deployments → Edit → New version** to update the existing URL.

Run `npm run test:rsvp-logic` for payload validation and transport checks. Browser tests use a stubbed Apps Script response and never write test guests to the live sheet. There is no lint script.
